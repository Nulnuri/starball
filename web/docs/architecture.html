스타볼 예측 파이프라인

네이버 스포츠 비공개 API에서 KBO 경기 데이터를 모아, LG 트윈스 스타볼의 매치데이 미션 3개에 넣을 값을 산출하고 ntfy 푸시와 PWA로 전달하는 파이프라인. 경기가 끝나면 박스스코어로 채점해 기록에 쌓는다. 의존성은 requests · pandas 뿐이고 배포는 깃헙 액션 + 깃헙 페이지다. 아래는 설계 근거, 실측으로 확인한 함정, 그리고 모델이 기준선을 못 이겼다는 측정 결과다.

가장 값진 발견은 preview다. 보통 가장 구하기 어려운 선발 투수의 특정 팀 상대 성적을 그냥 준다. KBO 공식이나 스탯티즈를 크롤링할 필요가 없었다.

실측으로 걸러낸 함정

함정 1 · yearMonth 파라미터가 무시된다

calendar?yearMonth=2026-09 는 200과 함께 8월 데이터를 돌려준다. 실제로 월을 고르는 건 date= 다. 둘 다 넘겨야 맞다.

조용히 틀린 답을 주는 종류라 파급이 컸다. 9월 이후 스케줄 실행이 전부 “경기 없음”이 되고, 3~8월을 훑는 상대전적 집계가 8월치를 6번 중복 계산하고 있었다. 평균값은 중복에 불변이라 겉으로 티가 안 났고, 축소에 쓰는 표본 크기만 부풀려져 있었다.

현재는 date=를 함께 넘기고, 응답이 요청한 달이 아니면 빈 리스트를 반환해 실패를 드러낸다.

함정 2 · seasonVsResult 의 집계 범위가 다르다

preview.seasonVsResult는 LG-NC 7승 5패(12경기)를 주는데, 일정에서 모은 실제 맞대결은 14경기였다. 대조해보니 3월 2경기를 빼고 센다. 승패는 이 필드에서, 득실점은 직접 모은 14경기에서 뽑고 있었으니 화면의 “상대전적”과 득실점 평균이 서로 다른 경기 묶음이었다.

현재는 승패까지 직접 모은 표본에서 다시 센다. 단일 출처 원칙.

함정 3 · KBO 이닝 표기

inn: "34.2"는 34.2이닝이 아니라 34와 2/3이닝이다. "108 1/3" 형태도 섞여 온다. 이걸 float로 그냥 읽으면 ERA·WHIP· 피홈런율이 통째로 어긋난다. parse_kbo_innings()로 분리하고 9케이스 단위테스트를 붙였다.

함정 4 · 볼넷 필드가 전 구단 null

offenseBb / defenseBb는 10개 팀 모두 null로 내려온다. 볼넷 관련 문항이 필요하면 offenseBbhp(볼넷+사구)로 대체해야 한다. HR·안타·삼진 필드는 결측 없이 깨끗하다.

기대 산출 — 오즈비(log5)

단순 산술평균 대신 리그 평균 대비 비율의 곱을 쓴다. 극단값에서 안정적이다. 득점과 카운팅 스탯(홈런·안타·삼진)이 같은 형태를 공유한다.

predict() · expected_runs / expected_count
# 공격력과 상대 실점력을 리그 평균으로 정규화해 곱한다
exp = league_avg × (off_rate / league_avg) × (def_rate / league_avg)

# 실점력은 선발의 예상 소화 이닝만큼만 선발 몫으로 잡는다
share    = starter.expected_ip / 9
def_rate = share × starter_ra9 + (1 − share) × bullpen_ra9

# 홈팀 가산 (KBO 홈 승률 ≈ .535)

축소 — 이 모델의 중심

작은 표본을 액면가로 믿으면 전부 망가진다. 오늘 예시만 봐도 LG 선발의 NC전 성적이 2이닝 ERA 9.00이었다. 모든 상대 한정 지표에 축소를 건다.

shrink(observed, prior, n, k)
shrink = (observed × n + prior × k) / (n + k)
# n == k 이면 정확히 반반. n 이 작을수록 prior(리그평균)에 붙는다.

PARK_FACTOR_REGRESSION = 0.5으로 1.0 쪽으로 절반 당겨서 쓴다. 구장당 홈경기가 60여 경기뿐인 노이즈도 있지만, 더 중요한 건 홈/원정 대비법의 구조적 편향이다. 어떤 팀의 ‘원정’에는 자기 홈구장이 빠지므로 비교 기준이 그 구장을 제외한 평균이 된다. 결과적으로 모든 구장의 팩터가 1.0에서 실제보다 멀어지는 방향으로 부풀려진다.

측정 원값은 park_factors.json에 보존하고 축소는 코드에서 한다 — 측정과 모델링 판단을 섞지 않는다. 0.5는 한 시즌 표본에 통용되는 보수적 값이며 유도된 상수는 아니다. 여러 시즌을 모으면 올려야 한다.

시뮬레이션마다 세 문항의 라벨을 붙이고, 조합별로 동시에 맞는 비율을 세어 최대인 조합을 고른다. 실측 효과는 크다 — 그리디 10.47% vs 조합 최적화 13.03%. (2026-08 측정. 그 뒤 드롭다운 구조와 모델이 바뀌어 지금 값과 다릅니다 — 최신 수치는 README 를 보세요.)

득점과 홈런을 독립으로 뽑고 있었고, 홈런 과산포도 크게 틀렸다. 득점을 조건으로 걸면 홈런은 거의 포아송이다 — 종전 φ=3.5 는 사실 득점 상관을 과산포로 잘못 흡수한 값이었다. 이제 그 팀의 득점 시뮬레이션에 묶어서 뽑는다(beta는 수치 보정으로 적합).

운영

배포

깃헙 액션 크론. cron: '0 1 * * *' = 01:00 UTC = 10:00 KST. 캐시 없는 신규 러너에서 21초 · 요청 23건으로 완료된다.

러너는 UTC다

date.today()를 쓰면 러너 로컬 날짜가 나온다. 한국시간 오전 9시 이전에 실행되면 어제 날짜로 경기를 찾는다. 크론이 5~30분씩 밀리는 걸 감안하면 언제든 터질 수 있었다. today_kst()로 고정했고, 한국은 1988년 이후 서머타임이 없어 고정 +9 오프셋이 항상 정확하다 (zoneinfo는 윈도우에서 tzdata를 요구하므로 피했다).

종료 코드 계약

코드의미워크플로 처리
0 예측 발송 완료 / 원정 경기(--home-only) / 경기 없는 날 초록
75 선발 예고 전 — NotReady 초록 + ::notice::
1 수집 실패 또는 푸시 실패 빨강 + ::error::

비게임일에 빨간 X가 뜨면 사용자가 고장으로 오해하고 결국 알림을 무시하게 된다. 그래서 NoGame/NotReady를 예외로 분리해 정상 종료로 흘린다.

ntfy 발행

헤더 대신 JSON 본문으로 발행한다. HTTP 헤더는 latin-1이라 한글 제목을 RFC 2047로 인코딩해야 하는데, 값이 길면 인코딩 결과가 줄바꿈되면서 requests가 거부한다(액션 라벨에서 실제로 터졌다). JSON은 그 문제가 없고 액션 버튼도 자연스럽게 실린다.

정산 — 실사용 성적 추적

예측만 하고 결과를 안 보면 실제로 맞았는지 영영 모른다. 백테스트 수치는 과거 재현이지 실사용 성적이 아니다. webdata.py settle 이 끝난 경기의 박스스코어를 받아 채점하고 기록에 남긴다. 채점 규칙은 backtest.py 의 것을 그대로 재사용한다 — 같은 규칙을 두 곳에 두면 반드시 어긋난다.

재현과 실사용을 섞지 않는다

시연용으로 지난 경기를 시점 고정 재현해 채워둘 수 있는데 (webdata.py backfill), 기록에는 replayed 표시가 붙고 화면에도 “몇 경기가 재현이고 몇 경기가 실사용인지” 나눠서 나온다. 섞어서 ‘N경기 성적’이라고 하면 거짓말이 된다.

재현을 build_context 로 하면 안 된다 — 과거 날짜에 오늘 시점 팀 성적이 들어가 미래를 훔쳐보고, 모든 경기가 똑같은 답이 나온다. 백테스트와 같은 누적 상태를 써야 한다.

PWA — 서버 없는 웹앱

깃헙 액션이 web/today.json 과 web/history.json 을 저장소에 커밋하고, 깃헙 페이지가 web/ 을 그대로 서빙한다. 정적 HTML 하나가 그 둘을 읽어 화면 3개(오늘·근거·기록)를 그린다. 서버도 빌드 도구도 프레임워크도 없다.

파일역할
web/index.html화면 전부(21KB, 의존성 0)
web/sw.js홈화면 실행용 서비스워커. 예측 데이터는 캐시하지 않는다 — 캐시하면 어제 값을 보여준다
web/manifest.webmanifest홈화면 추가 정보
web/*.json액션이 매일 덮어쓴다
깃헙 페이지는 공개 저장소에서만 무료다

그래서 저장소를 공개로 두어야 하는데, 그러면 코드에 박힌 기본 ntfy 토픽이 노출된다. 토픽은 이름만 알면 남이 발행도 할 수 있으므로, 워크플로가 NTFY_TOPIC Secret 이 없으면 아예 실패하도록 막았다. 기본 토픽으로 조용히 발송되는 일은 없다.

아래 수치는 2026-08 기준으로, 그때는 물리 시뮬레이션만 썼고 드롭다운 구조도 달랐습니다. 지금은 승패·홈런에 학습 모델을 쓰고 승패가 48.7% → 57.6% 입니다. 최신 수치는 README 에 있습니다.

모델은 기준선을 통계적으로 이기지 못했다. 13.03% vs 12.82% 는 468경기에서 1경기 차이이고 표준오차는 ±1.55%p 다. 조합 최적화가 그리디를 크게 이기는 것(+2.56%p)은 분명하지만, 그건 ‘모델 내부에서 상관을 제대로 다뤘다’는 뜻이지 ‘기저보다 낫다’는 뜻이 아니다.

기저 분포와 섞는다

모델 원본을 그대로 쓰면 오히려 손해였다(12.21%). 근거 없이 기저에서 벗어나기 때문이다. 그래서 리그 기저 분포와 섞어서 쓴다.

적중률 차이는 전부 표준오차 안이다 — 468경기에서 2경기 차이라 통계적으로 구별되지 않는다. 그래서 이 값은 정확도가 아니라 제품 판단으로 골랐다. α 가 낮으면 출력이 사실상 상수가 되어(92~100% 동일) 도구를 열 이유가 없어진다. 0.7 이면 5경기 중 1번은 다른 답이 나오면서 측정 가능한 손해는 없다.

과신 교정

모델이 65%라고 말한 예측이 실제로는 52.1%만 맞았다. 시뮬레이션이 입력 추정치를 확실한 값으로 취급해서 추정 자체의 불확실성이 빠진 탓이다. 브라이어 최소화로 적합한 PROB_CALIBRATION = 0.76 을 적용해 60~69% 구간 오차를 −12.9%p → −1.5%p 로 잡았다. 다만 보정은 순위를 바꾸지 않으므로 적중률은 그대로다 — 확률값을 믿을 수 있게 만들 뿐이다.

백테스트의 한계

미션 2·3 의 드롭다운 실제 선택지를 아직 못 봤다. 위 수치는 전부 추정한 구간 위에서 잰 값이라, 실제 선택지가 다르면 다시 재야 한다(build_base_rates.py 와 backtest.py 를 다시 돌리면 된다). 구장 팩터는 시즌 전체로 계산해 시즌 중반 예측에 약간 유출된다.

의도적으로 넣지 않은 것

자동 제출(Playwright)은 구현했다가 제거했다. 기술적으로는 쉽다 — 사이트에 전용 봇 탐지나 캡차가 없고, NetFUNNEL 가상 대기열은 실제 브라우저면 정상 통과한다. 넣지 않은 이유는 경품 이벤트 약관이다. 예측은 자동으로 받고 입력은 사람이 하는 현재 구조가 실익 대비 리스크가 가장 낮다고 판단했다.

데이터 출처는 네이버 스포츠 비공개 API이며 공식 지원이 없다. 폴라이트 딜레이 0.4초와 30분 TTL 캐시를 적용해 요청량을 하루 20여 건으로 유지한다. 예측은 확률 산출물이고 결과를 보장하지 않는다.
